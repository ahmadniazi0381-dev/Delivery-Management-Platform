# Naseeb Baryani & Pulao — Online Ordering Platform
### Project Roadmap & Technical Plan

**Shop:** Karachi Naseeb Baryani and Pulao — UCP branch (single location)
**Last updated:** July 9, 2026

---

## 1. Project Overview

A food ordering system for a single-branch restaurant delivering biryani, pulao, and related dishes within a fixed **2–2.2km radius** of the shop. Unlike Foodpanda-style platforms, there is no independent rider network — the shop owner dispatches their own delivery staff. The system has two actors: **Customer** and **Shop Owner**.

Three front-ends will share one backend:
- Customer mobile app
- Customer website
- Shop owner admin dashboard (web)

---

## 2. Actors & Features

### Customer
- Register/login: phone + password, or Gmail
- Phone OTP verification (2FA) required before an order can be placed
- Browse menu, search food, filter by category
- Add/remove items from cart
- Place order, pay via cash, bank transfer, JazzCash, Easypaisa, or credit/debit card
- Live order status tracking + order history
- Delivery availability check — blocked at checkout if the address is beyond ~2.2km from the shop

### Shop Owner
- Manage categories and menu items (add/edit/remove, mark unavailable)
- Manage discounts and offers
- Manage delivery charges
- Receive incoming orders, accept or reject
- Update order status: Pending → Preparing → Ready → Out for Delivery → Delivered
- View sales analytics (revenue, top items, order volume)

---

## 3. System Architecture

One backend, three clients:

```
Backend API (Node.js + Express, MySQL)
        |
        |-- REST endpoints (auth, menu, cart, orders, payments)
        |-- WebSocket / polling (order status push)
        |
   --------------------------------------------------------
   |                        |                              |
Customer Mobile App    Customer Website          Owner Admin Dashboard
React Native (Expo)    Next.js + TypeScript       React (Vite) SPA
```

All three clients call the same REST API, so business logic (pricing, delivery eligibility, order rules) lives in one place, not duplicated per client.

## 4. Recommended Tech Stack

| Layer | Technology | Why |
|---|---|---|
| Backend | Node.js + Express | Chosen |
| Database | MySQL + Prisma (or Sequelize) ORM | MySQL as specified; an ORM adds type safety and versioned migrations |
| Customer Mobile App | React Native (Expo) + TypeScript | One codebase for Android/iOS; Expo simplifies push notifications and updates |
| Customer Website | Next.js + TypeScript | Server-side rendering helps menu/landing pages get found on Google ("naseeb baryani ucp order online"); plain React + Vite is a simpler fallback if SEO isn't a priority |
| Owner Admin Dashboard | React (Vite) + TypeScript | Login-gated internal tool — no SEO need, faster to build than Next.js |
| Auth | JWT (access + refresh tokens), bcrypt, Google OAuth | Standard, well-supported in Express |
| Real-time order status | Socket.io, or short-interval polling as a simpler fallback | Pushes "status changed" events without needing a full GPS tracking system |
| Maps / distance | Google Maps Geocoding API + Haversine formula | Turns an address into lat/long, then checks straight-line distance against the shop |
| Image storage | Cloudinary, AWS S3, or local disk to start | Menu photos, category images |

| `otp_verifications` | OTP codes for phone verification | id, user_id, otp_code, purpose, expires_at, is_verified |

| `discounts` | Offers/discounts | id, title, type (percent/flat), value, scope (item/category/order), promo_code, start_date, end_date, is_active |
| `cart_items` | Active cart per user | id, user_id, menu_item_id, quantity |
| `orders` | Order header | id, customer_id, address_id, status, subtotal, delivery_charge, discount_amount, total, distance_km, payment_method, payment_status, placed_at, accepted_at, ready_at, out_for_delivery_at, delivered_at, cancelled_at |
| `order_items` | Line items per order | id, order_id, menu_item_id, item_name, unit_price, quantity, line_total |
| `payments` | Payment transaction records | id, order_id, method, transaction_ref, amount, status, gateway_payload, created_at |

Since this is a single branch, "owner" is just a role in `users` rather than a separate multi-tenant structure — no need for the restaurant-per-vendor complexity a Foodpanda-style schema would need.

## 6. Authentication & OTP (2FA) Flow

1. Customer registers via phone + password, or Gmail OAuth. Account starts with `phone_verified = false` unless already confirmed.
2. Customer can log in and browse/cart freely without a verified phone.
3. At checkout (first order, or whenever the phone isn't yet verified):
   - Customer confirms their phone number
   - Backend generates a 6-digit OTP, stores it in `otp_verifications` with a short expiry (e.g., 5 minutes), sends it via SMS API
   - Customer enters the code; backend verifies and sets `phone_verified = true`
   - Order placement proceeds only after verification succeeds
4. Later orders skip OTP since the phone is already verified (until the number is changed).

---

## 7. Delivery Radius Logic

1. Customer enters/selects a delivery address (manual entry or map picker)
2. Address is geocoded to latitude/longitude (Google Maps Geocoding API)
3. Straight-line distance from the shop's fixed coordinates is calculated with the Haversine formula:

```
a = sin²(Δlat/2) + cos(lat1) · cos(lat2) · sin²(Δlong/2)
c = 2 · atan2(√a, √(1−a))
distance = R · c        (R = 6371 km)
```

4. If `distance ≤ max_delivery_km` (configurable, default 2.2km) → order allowed
5. If `distance > max_delivery_km` → checkout blocked with a clear "outside delivery area" message
6. Run this check both when the address is saved *and* again at checkout, in case the owner later tightens the radius

---

## 8. Order Lifecycle

```
Pending → Accepted → Preparing → Ready → Out for Delivery → Delivered
   |          |
   |          └──→ (owner can still cancel in edge cases)
   └──────────────→ Rejected (owner declines)
   └──────────────→ Cancelled (customer cancels pre-acceptance)
```

- **Pending → Preparing → Ready → Out for Delivery → Delivered** is the flow you specified
- **Rejected** / **Cancelled** are recommended additions so every order reaches a clean end state instead of hanging

---

## 9. Payment Methods

- **Cash on Delivery** — no integration, just a flag on the order
- **Bank Transfer** — simplest to build first: customer enters a transaction reference, owner manually confirms in the dashboard
- **JazzCash / Easypaisa / Card** — two paths:
  - **Direct integration**: a separate merchant account and API credentials with JazzCash and with Easypaisa individually, plus a separate card gateway. More setup work, but no aggregator fee on top.
  - **Payment aggregator**: services such as PayFast, Safepay, Simpaisa, XPay, or a bank gateway (HBL Konnect, Bank Alfalah's Alfa Payment Gateway) bundle JazzCash + Easypaisa + cards + bank transfers under one integration and one dashboard, so you onboard once instead of separately with each wallet. Typical fees across providers run roughly 2–3.5% per transaction, and onboarding is generally faster than going direct with each wallet.
  - For a single-branch shop just starting out, the aggregator route usually means less overhead — worth getting quotes from 2–3 before committing, since terms and fees shift.

`GET /owner/orders` · `PUT /owner/orders/:id/accept` · `PUT /owner/orders/:id/reject` · `PUT /owner/orders/:id/status`

`POST/PUT/DELETE /owner/categories` · `POST/PUT/DELETE /owner/menu-items`

**Discounts — Owner**
`POST/PUT/DELETE /owner/discounts`

**Analytics — Owner**
`GET /owner/analytics/sales` · `GET /owner/analytics/top-items`

**Payments**
`POST /payments/initiate` · `POST /payments/webhook` · `GET /payments/:orderId/status`

## 13. Open Questions to Confirm Before Building

- Exact GPS coordinates of the shop (needed for accurate distance calculation)
- Payment approach: direct merchant accounts with JazzCash/Easypaisa, or an aggregator (PayFast, Safepay, Simpaisa, etc.)?
- SMS/OTP provider — worth a short comparison for reliability and per-SMS cost before committing; many exist and quality varies
- Does "live tracking" mean GPS map tracking of the delivery employee, or just live status updates (Preparing/Ready/etc.)? This significantly changes Phase 4/7 scope
- Existing branding: logo, menu photography, color palette — or design from scratch?
- Hosting budget/preference for deployment (shared hosting, VPS, cloud)
- Should the owner dashboard be responsive for phone-browser use, since day-to-day order management will likely happen on the go?
